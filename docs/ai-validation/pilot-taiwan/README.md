# 台湾样例：标准字段与结果读取草案

状态：候选试点、未启用。只完成本地结构分析，不代表 AI 引擎已实现或财务结果已验证。

## 选择依据

本地 Coral Sea 台湾资料有两个月的原始工资表和对应历史 PN，适合先验证相同表头、人数变化及中英文实体信息。供应商 ID、客户数据库 ID、profileId、生效模板版本和线上 Mapping 尚未核实，不将文件名当作已配置的生产组合。

历史 PN 是结构参考，不能直接当作人工标注的正确答案；未重新运行转换、Excel／Spire 重算或 AI 采集。

## 三份配置

- schema.v0.json：13 个员工级金额字段及比较语义，是业务字段定义草案，不是完整的 JSON Schema 输出校验器。
- source-hints.v0.json：仅包含原始账单的字段标签、定位提示、币种和账期依据，可供未来独立采集流程使用。
- code-result-binding.v0.json：读取最终工作簿 TW 采集明细的绑定和母版哈希，仅供代码侧使用，禁止传给 AI。

`schema.v0.json` 与 `code-result-binding.v0.json` 现可供 `bill_validation` 离线读取器使用，须显式允许草案并提供可信员工任务清单。`source-hints.v0.json` 尚无 AI 运行时消费者。所有金额容差为零的设置仅用于后续离线精确差异诊断，当前读取器不执行比较，生产容差尚未定；自动通过均关闭。

## 特殊项与待确认问题

1. 供应商 Service Fee 与客户侧 Recurring／Management Fee 不直接等同。原服务费作为已知但未纳入本次比较的字段保留，不能误报为“未知”或直接映射到客户管理费。
2. 病假扣款在现有 apply_sick_leave_formula 中依据时薪和病假小时重算。原表列示值与代码重算值可能出现舍入差异，需明确规则；先报告差异，不自动忽略或套用全局容差。
3. 加班汇总纳入核验，加班档位明细暂未纳入本轮对比，须显示覆盖范围。旧 _pending_ask_colleagues_tw_ot_skip.md 仍说默认跳过明细，但当前代码默认只跳过 Service Fee。这是文档与代码的差异，不能按旧说明推断当前行为；线上组合 Mapping 是否另行跳过尚未核实。
4. 本地母版 TW!Q9（伙食补贴）与 TW!R9（Remote Stipend）都引用 TW-L!R9。两者是否有意共用来源需确认；存在伙食补贴时可能影响汇总。当前仅记录，不修改模板或视作已确认业务规则。
5. 供应商源表没有已核实的内部员工编号。先保留原文中英文姓名，唯一匹配后关联内部员工；同名或无法唯一匹配需复核，不能把代码选出的员工匹配答案提供给 AI。
6. TW!C 为内部员工编码来源，PN 发票号、客户地址、管理费、汇率、税额、Outstanding 等不应都强制要求 AI 从供应商原账单采集。
7. 模板默认值和历史 PN 缓存不作为现算结果。代码读取公式值前必须成功重算，结果绑定文件修订；本次只验证标签及公式关系。

## 本次核实结果

最初 XML 检查中，共享公式的子单元格没有自己的公式正文；随后改用 openpyxl 只读解析确认。没有把缺少独立 XML 公式文本当作实际公式错误。
